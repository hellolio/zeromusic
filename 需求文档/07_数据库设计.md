## 2. 设计原则

1. **songs 只存元数据，不存顺序**。可变的「播放顺序」独立存放（见 `queue_items`）。
2. **排序/可变状态与元数据解耦**，避免重排污染媒体库。
3. 一切多对多关系用**关联表**（`songs_tags`）。
4. 能落库的结构化文本（歌词）**用数据库**，不散落文件。
5. 临时过程数据（导入进度）**不落库**，只在内存维护。
6. 外键启用级联删除，保证引用一致性。

## 4. 各表详细定义 + 使用方式

> 建表语句统一存放在 `sql/create_tables.sql`，本文档只说明表结构与使用方式，不再内嵌 SQL。

### 4.1 `songs` — 媒体库

字段：`id, title, artist, album, genre, duration_ms, media_type(0音频/1视频), file_path(UNIQUE), cover_path, is_favorite, play_count, last_played_at, created_at`
索引：`is_favorite / last_played_at / artist / album / title / media_type`

**使用方式**
- **播放列表页分类**：全部=`全部`；专辑=按 `album` 分组；艺人=按 `artist` 分组；收藏= `WHERE is_favorite=1`；最近=`ORDER BY last_played_at DESC`；视频= `WHERE media_type=1`。
- **点歌即播**：`MediaRepository` 按当前筛选条件查出一组 songs → 交给 `QueueController` 初始化队列。
- **编辑信息**（01·3.6）：`UPDATE title/artist/album/genre`。
- **删除**（01·3.7）：`DELETE` + 级联清理 `songs_tags`、`queue_items`、`lyrics_cache`。

---

### 4.2 `tags` — 标签

字段：`id, name(UNIQUE), color`

**使用方式**
- **自定义标签**（01·3.5）：创建/重命名/删除/打标/取消打标。
- **内置来源标签**（替代原 import_tasks）：导入歌曲时同时写入一条内置标签，如 `来源:云端`、`来源:设备`、`来源:WiFi`。通过 `songs_tags` 关联，筛选来源即 `WHERE tag = '来源:云端'`。
- 删除标签：`DELETE`，级联清理 `songs_tags` 记录。

---

### 4.3 `songs_tags` — 歌曲与标签关联（多对多）

字段：`song_id, tag_id`（复合主键，双外键级联删除）
索引：`(tag_id)` 用于按标签筛选

**使用方式**
- 打标签：`INSERT OR IGNORE INTO songs_tags(song_id, tag_id) ...`
- 取消：`DELETE FROM songs_tags WHERE song_id=? AND tag_id=?`
- 按标签筛选歌曲：`SELECT s.* FROM songs s JOIN songs_tags st ON st.song_id=s.id WHERE st.tag_id=?`
- 一首歌的标签列表：`SELECT t.* FROM tags t JOIN songs_tags st ON st.tag_id=t.id WHERE st.song_id=?`

---

### 4.4 `queue_items` — 当前播放队列（方案 B）

字段：`position(主键, 即顺序), song_id(外键级联删除)`

**使用方式（重要）**
- 队列是**当前播放顺序**的持久化，重启后完整还原。
- **播放整个歌单/筛选结果时**：一次性批量 `INSERT`（单事务事务）所有行，`position` 从 0 递增。此后**下一首/上一首/暂停/继续全部在内存用指针进行，不写数据库**。
- **插歌/移除/重排时**：仅对受影响的行做 `INSERT`/`DELETE`/`UPDATE position`（正常量的 O(1) 操作，用事务保证一致）。
- 读队列顺序：`SELECT song_id FROM queue_items ORDER BY position`，再按 id 批量查 `songs` 取元数据。
- 清空队列：`DELETE FROM queue_items`。
- 播放指针（当前第几首）**不落库**，仅在内存（`QueueController` 维护 currentIndex）。

> 为什么不用 JSON 单行：单行方案每次增删都要整行重写；逐行方案仅在开始播放时批量写一次，之后增删 O(1)。详见《整体构架.md》讨论记录。

---

### 4.5 `lyrics_cache` — 歌词缓存

字段：`id, song_id(UNIQUE, 外键级联删除), lrc_text`

**使用方式**
- 首次读取/匹配歌词后写入缓存；再次播放同一首直接取库，避免重复解析文件或网络请求。
- 无歌词显示"暂无歌词"（02·3.6），不会写入本表。
- 歌曲删除时级联清除对应歌词缓存。

## 5. Repository 抽象层

| Repository | 表 | 职责 |
|------------|----|------|
| `MediaRepository` | songs | 扫库写入、查询/分类、编辑、删除、播放统计更新 |
| `TagRepository` | tags / songs_tags | 标签 CRUD、打标、按标签筛选 |
| `QueueRepository` | queue_items | 队列批量初始化、增删、重排、读取 |
| `LyricsRepository` | lyrics_cache | 歌词缓存读写 |

> Repository 对上层屏蔽 drift；业务层（UI / services）只依赖 Repository 接口。

---

## 6. 与设置页的边界

- 主题 / 语言 / 减弱动效 / 默认音量等**偏好**用 `shared_preferences`（见 05 设置页 · 6），**不进入数据库**。
- 数据库只管**业务数据**：媒体库、标签、队列、歌词缓存。

---

## 7. 索引策略小结

| 表 | 索引 | 服务查询 |
|----|------|----------|
| songs | favorite / last_played_at / artist / album / title / media_type | 全部分类标签切换 |
| songs_tags | (tag_id) | 按标签筛选歌曲 |
| queue_items | 主键 position 即有序 | 队列顺序读取 |

## 8. 验收要点 / 测试用例范围

- 表结构可用 drift 建表成功，SQL 与 ORM 定义一致。
- 分类筛选（全部/专辑/艺人/收藏/最近/视频）结果正确。
- 标签创建/删除/打标/按标签筛选正确。
- 删除歌曲级联清理标签关联、队列引用、歌词缓存。
- 队列：批量初始化、下一首（不改库）、插歌/移除/重排、重启还原。
- 歌词缓存读写与级联删除正确。
- 完整用例见《测试用例/数据库设计_测试用例.md》。
