## 二、功能实现概要

- 实现功能点：
  - 桌面端专属透明置顶歌词条：双行（当前句高亮 + 下一句）、间奏「♪ 间奏 ♪」占位、
    无歌词「歌名 · 歌手」、未播放「未在播放」；字号三档（小/中/大）、任意拖拽、✕ 关闭、
    恢复默认位置，全部持久化（`desktopLyrics.enabled/fontSize/offset`）。
  - 仅桌面端出现设置分组（`DeviceType` 断点 + `Platform.isDesktop` 双门控），移动端 stub 不编译原生代码。
- 核心组件/服务：
  - `services/desktop_lyrics/lyric_window_api.dart`：`LyricWindowApi` 接口 + provider 注入
    （桌面真实现 / 移动 stub），业务零依赖 desktop_multi_window。
  - `lyric_bar_messenger.dart`：**纯 Dart** 跨窗口契约（状态/配置/回传事件编解码 + 容错回退），
    主窗口与子窗口共用，contract 可单测。
  - `lyric_window_desktop.dart`：真实现 + 几何纯函数（`lyricBarWindowSize`/`defaultLyricBarPosition`/
    `clampLyricBarPosition`）；窗口**只建一次复用**（open 时已存在 → configure+show）。
  - `desktop_lyrics_controller.dart`：`Notifier<bool>` 镜像开关偏好；歌词行状态经
    `select` 去重节流（行内进度不推送），消息 `==` 相等不下发；回传事件（✕/位置）只写偏好，
    窗口同步全部交给响应式重建——单数据流，无命令式分支。
  - `ui/desktop_lyrics/desktop_lyrics_bar.dart` + `lyric_bar_app.dart`：歌词条 UI 与子窗口
    Flutter 引擎入口（`runLyricBarWindow()`），拖拽走 `windowManager.startDragging()` 原生模态。
  - 三端 runner 注册：`setOnWindowCreatedCallback`（macOS Swift / Windows C++ / Linux C），
    仅对多窗口子进程应用无边框透明置顶样式，主窗口不受影响。
- 关键技术点：desktop_multi_window 的子 FlutterEngine 无法销毁 → 开关切换走
  hide/show/configure 而非创建/销毁；`LyricWindowConfig ==` 幂等去重避免重复下发。

## 三、遇到的问题与解决（坑）

### 坑 1：`WidgetsBinding.instance` 在纯 `test()` 未初始化 → 编排链被静默吞掉
- **现象**：控制器测试全部失败（窗口未打开/偏好未写入），但无异常栈——`unawaited(_syncWindow(...))`
  把错误吞进孤儿 Future，测试只表现为「什么都没发生」。
- **根因**：`_buildConfig` 用 `WidgetsBinding.instance.platformDispatcher.platformBrightness`
  判断暗色；纯 `test()`（非 `testWidgets`）没有初始化 WidgetsBinding，直接抛
  `Binding has not yet been initialized`。
- **解决**：改用 `dart:ui` 的 `PlatformDispatcher.instance.platformBrightness`——无需 binding、
  生产语义等价（WidgetsBinding.platformDispatcher 本就是它的转发）。
- **教训**：控制器/服务层应尽量依赖 `dart:ui` 级 API 而非 WidgetsBinding，可测性天然更好；
  `unawaited` 的后台链路要在测试里主动验证副作用，否则异常被吞。

### 坑 2：Riverpod 3 所有 Provider 默认 autoDispose → 测试里控制器「读完即焚」
- **现象**：`container.read(controllerProvider)` 后无论怎么 pump，窗口都不打开、事件订阅不生效。
- **根因**：测试里只有 `read`（临时订阅，读完释放）→ 控制器元素失去监听者即被销毁 →
  `_syncWindow` 的 `ref.mounted` 守卫直接 return、`events.listen` 被 `onDispose` 取消。
  生产中 `MyApp` 的 `ref.watch` 恰好充当常驻保活，掩盖了该语义。
- **解决**：测试用 `container.listen(controllerProvider, (_, _) {})` 挂持久 listener 保活
  （等价于生产 MyApp 的 watch）。`ref.mounted` 守卫本身是对的——它正确拦下了销毁后的同步。
- **教训**：Riverpod 3 的 autoDispose 默认值改变了「read 一下就算初始化」的旧直觉；
  凡是「全局单例型 Notifier」，要么有常驻 watch，要么在测试里显式保活。

### 坑 3：`ProviderContainer.pump()` 不级联刷新依赖重建
- **现象**：保活后仍偶发同步不到：偏好从 AsyncLoading→AsyncData 后，控制器重建没有随之发生。
- **根因**：`pump()` 只 `await scheduler.pendingFuture`——等的是**当前**这一批调度，
  不追级联（依赖变更 → 标脏 → 新一轮调度）。
- **解决**：测试 settle 改为循环冲刷（`for 8 次 { await pump(); await Future.delayed(Duration.zero); }`），
  覆盖微任务与调度级联。
- **教训**：Riverpod 测试的「等一下」要写成有界循环而不是固定次数；链路每多一跳 Async，
  就多一轮 pendingFuture。

### 坑 4：C/C++ runner 在 macOS 上的 21 条「编译错误」全是分析器假阳性
- **现象**：给 linux/windows runner 加插件注册回调后，clangd 报 21 条 STOP 级错误
  （`'gtk/gtk.h' file not found`、`flutter::` 未知类型等），且行号落在未改动的模板代码上。
- **根因**：在 macOS 上分析 Linux（GTK 头）/ Windows（Win32 头）runner，交叉头文件路径不存在，
  错误沿 include 链级联放大；与本次改动无关。
- **验证方法**：`git stash` 恢复未改动的原始模板 → 跑同样的诊断 → 报**一模一样**的错 →
  `git stash pop` 恢复改动。即「原始模板也报错 = 环境误报」的对照实验。
- **教训**：跨平台仓库里 LSP 对非宿主平台原生目录的诊断不可直接采信；
  analysis_options 已排除 platform 目录，DoD 以 `flutter analyze`（lib/ + test/）为准。
- **附带坑**：pi-lens 的 advisory `lyric_window_api.dart 引用 lyric_window_desktop.dart` 在文件
  创建后仍多次出现（缓存过期），以 LSP 全量扫描 + analyze 双绿为准忽略。

### 坑 5：macOS 上 `windowManager.show()` 会抢焦点
- **现象/风险**：`window_show` / `windowManager.show()` 内部走 `NSApp.activate`——用户点歌词条
  任意位置都会把主应用拉到前台，违背「点击不抢焦点」需求。
- **解决**：macOS 自建 `zeromusic/lyric_window/orderFront` 原生通道，MainFlutterWindow.swift 里
  `orderFront(nil)`（只显示不激活）；borderless `CustomWindow` 不覆写
  `canBecomeKeyWindow` → 天然不成为 key window。非 macOS 平台 `stealsFocusOnClick = true`
  并在设置页如实提示。

### 坑 6：细节备忘
- **AnimatedSwitcher 没有 `curve` 参数**——曲线要写在 transitionBuilder 的 Tween 里；
  用对称 Tween（`Offset(0,-0.6)→zero`）让出句复用入场动画反放，一行代码同时满足
  「新句下滑入、旧句上滑淡出」。
- **flutter_riverpod 3 的 `Override` 类型移到了 `misc.dart`**，`import 'package:flutter_riverpod/misc.dart'`
  才能在测试辅助函数签名里用 `List<Override>`。
- **间奏态单行设计**：`currentText == ''` 时第二行整体不渲染（而非显示下一句），
  避免间奏标记与下一句并排的割裂感。
- **`WindowController` 的 Dart 侧 API 很薄**：无 `close()`/`setFrame()`；`WindowMethodChannel.invoke`
  的 `mode:` 是命名参数——封装进 `LyricBarWindowCommands` 隔离，别让业务碰原始 API。

## 六、缺陷修复回补（2026-09，首次真机验证前）

> 首轮实现虽单测全绿，但 macOS 原生层从未编译过、且跨窗口初始化时序有硬伤，
> 真机首开即暴露。以下三个坑均为「单测绿 ≠ 功能可用」的实证。

### 坑 7：`FlutterViewController` 没有 `window` 成员 → macOS 整包编译失败
- **现象**：`flutter build macos` 直接失败：`value of type 'FlutterViewController' has no member 'window'`。
- **根因**：`setOnWindowCreatedCallback` 回调拿到的是 `FlutterViewController`（NSViewController
  子类），取宿主 NSWindow 必须经 `view.window`（此刻 `contentViewController` 已挂载，view
  必在窗口层级内）。想当然写了 `controller.window`，而 runner 代码不参与 `flutter analyze`，
  提交前也没跑过原生构建。
- **教训**：动了 runner / 原生插件的提交，DoD 必须加 `flutter build <platform>`，
  analyze + test 双绿不够。

### 坑 8：`hiddenAtLaunch` 创建的窗口「首次打开永远不出现」
- **现象**：首次开启开关（或重启自动恢复）歌词条不出现；只有关→再开（走复用分支
  configure+show）才出现。
- **根因**：窗口以 `hiddenAtLaunch: true` 创建（为避免错误位置闪现），但 show 只存在于
  「复用已有窗口」分支；首次创建路径上主窗口、子窗口都没人调 show。
- **解决**：增加 **ready 握手**——子引擎注册完 push handler 后回发 `ready` 事件；主窗口
  收到后才下发 show 并立即补推当前态。顺带修复另一个时序缺陷：冷启动窗口期的行推送
  会因子引擎尚未注册 handler 被通道丢弃（丢一行就要等下一次行变更，最长半分钟）。
- **教训**：跨窗口/跨进程初始化要显式握手（ready 信号）而不是双方各自猜时序；
  「创建时隐藏、就绪后显示」的模式里，show 的触发者必须唯一且由就绪方通知。

### 坑 9：关闭再重开后展示陈旧行
- **现象**：✕ 关闭后再开，歌词条停在关闭前的那一行（直到下一次行变更）。
- **根因**：隐藏期间推送被抑制（`_open == false` 时 pushState 直接丢弃），复用路径的
  `configure` 虽携带最新 `initialState`，但子窗口只更新了 `_config` 没应用到 `_state`。
- **解决**：① 子窗口 `didUpdateWidget` 应用 `config.initialState`；② 控制器在 `open()`
  完成后即推一次当前态（fake/测试可断言，真实路径由 ready 补推兑底）——双保险。
- **教训**：配置消息携带状态快照时，消费端要真正应用它；「暂停推送」的通道必须
  在恢复可见的那一刻做状态对齐，否则视觉层永远停在暂停点。

## 七、真机反馈修复（背景透明 / 自适应高度 / 悬停交互 / 设置简化）

### 坑 10：窗口设了 clear 背景仍不透明 —— `FlutterViewController` 自绘黑底
- **现象**：NSWindow 已 `isOpaque=false` + `backgroundColor=.clear`，歌词条后面仍有一层底色。
- **根因**：`FlutterViewController` 实例化时把 contentView（FlutterView）的背景色
  置为黑色（官方头文件原文："The contentView (FlutterView)'s background color is
  set to black during its instantiation"），窗口与控制器背景是**分别持有**的。
- **解决**：创建回调里补一句 `controller.backgroundColor = .clear`，窗口级透明才真正生效。
- **教训**：macOS 的全透明窗口 = 窗口透明 + FlutterView 透明两层都到位；
  只调一层会出现「明明都设了 clear 却仍不透明」的谜之底色。

### 坑 11：固定窗口高度的死区与自适应
- **现象**：歌词条窗口按字号档位固定高（84/96/112），文字只占上半部，下半部悬空——
  背景不透明时看起来像一条厚板；拖拽热区也比可见内容大。
- **解决**：子窗口实测内容高度（`_ContentHeightReporter` 渲染层量测）→
  `windowManager.setSize(width, ceil(高度))`；宽度仍按字号档位。
- **关键语义**：window_manager 的 setSize 是**顶边固定**（原生 `origin.y += 旧高-新高`），
  行数 2↔1 切换时当前行位置不跳动；首帧收缩发生在 show 之前，肉眼无感。
- **注意**：复用路径的 reconfigure 会把窗口重置回档位尺寸，需在 `didUpdateWidget`
  后重放一次高度应用（保留 `_lastContentHeight`），否则主题/语言类变更后死区回归。

### 设计调整：悬停才显示淡底与 ✕
- 平时完全透明、无任何控件；鼠标悬停 → surface 25% 淡底 + ✕（透明度 0→1、
  缩放 0.6→1、`IgnorePointer` 随悬停解禁）。
- ✕ 常驻树内（不条件移除），布局尺寸稳定，避免悬停时行内抖动；
  测试用例 TC-20 因此改为「先悬停再点击」，并新增 TC-20b 拦截断言。
- 平台限制备忘：Flutter 的 `BackdropFilter` 只能模糊自己场景内的内容，
  「稍微模糊的背景」用柔和半透明底色实现；真毛玻璃需原生 `NSVisualEffectView`。
- **扩展（悬停播放控制条）**：同一悬停门控模式复用到右侧控制排
  （音量滑杆 + ⏮⏯⏭）：Stack 内控制条用 `Positioned` 悬浮在歌词层之上，
  歌词层保持非定位子级继续驱动窗口高度量测；控件间间隙命中穿透到底层
  （拖拽不受影响）。⏯ 图标形态与音量初值都来自状态推送的 isPlaying/volume；
  音量拖动中仅本地覆写反馈，onChangeEnd 才回传（防跨窗口通道刷屏），
  主窗口写回默认音量偏好（与播放页同源，单一事实源不变）。

### 设置页简化
- 开关改用 `CupertinoSwitch`（与均衡器一致，iOS 风格统一）。
- 字号 / 恢复位置子项仅在开关打开后显示（渐进披露），关闭态只剩一行。

### 坑 12：帧回调内 setSize → Impeller `SetupRenderPass` SIGSEGV（严重）
- **现象**：bc7c07a（高度自适应上线）之后，桌面歌词条在切歌/行数变化时随机闪退。
  崩溃签名高度一致：`EXC_BAD_ACCESS (SIGSEGV)` at 0x0，Thread 12
  `io.flutter.raster`，`impeller::Canvas::SetupRenderPass()`；主线程栈顶部：
  `WindowManager.setBounds` → `FlutterView.setFrameSize` →
  `ResizeSynchronizer.beginResize` → `FlutterRunLoop.pollFlutterMessagesOnce` →
  `PlatformConfiguration::BeginFrame` —— resize 平台消息被**在帧处理事务中同步泵入**
  （帧内重入），与 raster 线程竞态拿到空的渲染目标。
- **根因**：`_ContentHeightReporter` 在 `addPostFrameCallback`（帧回调）里直接调
  `windowManager.setSize`。平台消息处理嵌在帧回调/渲染事务栈上，属于引擎已知时序
  竞态（同族 issue：flutter/flutter#183623 程序化 resize 风暴 + #185394 同签名），
  「行数频繁变化 + active rendering」正是最易触发的窗口期。
- **解决**：新增 `LyricWindowResizeGate`（`lib/services/desktop_lyrics/`），高度应用
  三重收敛：① **去抖**（150ms 合并为最新值）；② **单飞串行**（同一时刻最多一个
  setSize 在途，在途请求排队）；③ **错峰**（应用发生在独立的定时器轮次，不再嵌在
  任何帧回调/平台消息栈里）。复用路径 reconfigure 用 `gate.reset()` 强制重放。
  另：reconfigure 幂等判定改用 `LyricWindowConfig.sameDisplayIgnoringState`
  （忽略 initialState），否则音量/播放态的每次状态推送都会触发整轮 configure
  （多两次无谓 resize，放大风险窗口）。
- **教训**：① **绝不在帧回调 / 帧处理栈内调用会同步泵平台消息的窗口 API**
  （setSize/move 等）；窗口尺寸变更应错峰到安静的事件循环轮次。② 引擎层竞态
  上游未修时，应用层用「去抖 + 串行 + 幂等」把触发频率压到零是可行的止血手段；
  纯 Dart 的 fakeAsync 单测（TC-39）把这个时序约定固化成回归护栏。

### 坑 13：控制条点击无反应 + 点击歌词条把主窗口带到最前
- **现象 ①**：悬停控制条（⏯/⏮/⏭/音量）点击毫无反应。
  **根因**：UI 层（DesktopLyricsBar）与主窗口事件处理都齐备，唯独壳层
  `lyric_bar_app.dart` 的 build 里没把 4 个新回调接到 `DesktopLyricsBar`
  （仍只接 onClose/onDragStart）——回调悬空，纯静默失败。widget 测试
  TC-33~36 只覆盖了 UI 层回调发射，跨过接线层直达主窗口的链路无护栏。
  **解决**：壳层补齐 4 个回传方法（统一 `_sendHostEvent`：timeout + 异常
  静默降级）；TC-40 泵真实 LyricBarApp + 拦截 desktop_multi_window 底层
  通道，验证四个控件点击后 back 通道事件序列，把接线固定下来。
  **教训**：UI 层 widget 测试验证不了「接线层」；新增跨窗口回调时必须
  在壳层加一条端到端（拦截底层通道）的断言。
- **现象 ②**：点击歌词条时，被遮挡的主窗口跳到最前。
  **根因**：borderless 只保证窗口不可成为 key（注释里「不抢焦点」的理解
  是错的）；点击任何窗口时 AppKit 默认仍会**激活整个 app**（NSApp.activate
  → arrangeInFront），同一 app 的主窗口随之 orderFront。窗口绑定验证：
  window_manager 0.5.2 用 `registrar.view?.window` 绑定当前引擎自己的窗口，
  子引擎的 startDragging/setSize 都正确作用于歌词条，拖动误拖主窗口可排除。
  **解决**：子窗口 styleMask 加 `.nonactivatingPanel`（悬浮窗标准做法）：
  点击不再激活 app；置顶层级（floating）不变。歌词条与主窗口置顶完全独立。
  **教训**：「不抢焦点」= 不可成为 key 窗口（canBecomeKey）≠ 不激活 app；
  悬浮窗要两层都处理（borderless + nonactivatingPanel）。
- **（坑 14 修正）**：此处原文「鼠标 hover 不依赖 key window，tracking area
  照常工作」是错的 —— Flutter 引擎的 hover 事件另有 `mouseTrackingMode`
  开关，默认只在 app 激活时投递（见坑 14）。

## 八、第二轮真机反馈修复（高度 / 对齐 / Dock / 悬停失效）

### 坑 14：nonactivatingPanel 后悬停完全失效，点击后控制条卡住不消失
- **现象**：歌词条改为不激活 app 后，鼠标悬停不再浮现控制条；点击歌词条
  后控制条出现但**永不消失**（移开鼠标也无济于事）。
- **根因**：Flutter macOS 引擎对 hover 事件（tracking area 的
  mouseEntered/Exited/Moved）有自己的开关 —— `FlutterViewController.
  mouseTrackingMode`，默认为 `InActiveApp`，即 **hover 事件只在 app 激活时
  才投递给 Flutter**（上游 flutter/flutter#165073、#185426）。歌词条是
  nonactivating 窗口，app 永远 inactive → enter/exit 被引擎过滤。
  而 mouseDown 不受该开关过滤：点击后 framework 收到 PointerAdd，
  MouseRegion 判定指针在区域内触发 onEnter → 控制条出现；移开需要的
  PointerRemove（来自 mouseExited）被过滤 → onExit 永不触发 → 状态卡死。
  两个现象同一根因，精确对应默认 InActiveApp 的过滤行为。
- **解决**：子窗口创建回调里 `controller.mouseTrackingMode = .always`
  （公开 API，悬浮窗场景官方设计）—— hover 事件不依赖窗口/app 焦点。
  主窗口无需改动（regular 窗口激活路径不受影响）。
- **验证方法**：头文件 `FlutterViewController.h` 的枚举注释直接写明
  「when the view is in the active app」；nm/strings 查二进制确认属性。
- **教训**：排查平台层 hover 问题时，别只看 tracking area options ——
  Flutter 引擎在 NSResponder 之上还有一层 mouseTrackingMode 过滤；
  「点击后才生效 + 永不消失」是 enter 事件丢失 exit 的典型指纹。

### 坑 15：歌词条开着时点 Dock 图标唤不出主窗口
- **现象**：歌词条显示中，点击 Dock 图标 app 激活了但主窗口不出现；
  关闭歌词条后恢复正常。
- **根因**：macOS 点击 Dock 图标触发 `applicationShouldHandleReopen:
  hasVisibleWindows:`，系统只在**没有任何可见窗口**时才自动唤出主窗口。
  歌词条是常驻可见窗口 → hasVisibleWindows 恒为 true → 系统/基类认为
  「app 已有可见窗口」而不动作。
- **解决**：AppDelegate 覆盖 reopen：显式
  `MainFlutterWindow.bringMainToFront()`（makeKeyAndOrderFront：最小化
  会解除最小化、被 close 会重新显示，均符合「唤出」预期，幂等无害），
  返回 true 走系统默认后续处理。该方法在 engine 的 FlutterAppDelegate
  生命周期协议中已声明但实现为「flag=true 不动作」，Swift 子类
  `override func applicationShouldHandleReopen(_:hasVisibleWindows:)`
  即可（Headers 里 grep 不见是因为声明在协议/生命周期 delegate 头中；
  直接写同名方法会报「requires an 'override' keyword」）。
- **教训**：常驻悬浮窗会让 macOS 的「无可见窗口」判定永远不成立；
  带 NSPanel/浮层的 app 都应自己处理 reopen。确认 ObjC 父类是否声明了
  某方法，grep 头文件不够 —— 协议/生命周期 delegate 头里可能有；
  最快路径是直接写 override 看编译器怎么说。

### 设计调整：高度固定两行 + ✕ 与控制条同行
- **高度**：窗口高度恒定为两行内容高度，无下一句/间奏/占位时第二行以
  空格占位渲染（不渲染会塌陷导致高度跳动）。比「行数变化重算高度」
  更稳：gate 只需在首帧/reconfigure 应用一次，行数变化零 setBounds。
- **✕ 对齐**：✕ 从独立 Positioned（右上角）移入控制行 Row 尾部
  （同一 AnimatedOpacity/IgnorePointer 门控内），与 ⏮⏯⏭ 垂直居中
  自然对齐；TC-33 布局断言改为「✕ 中心与控制钮中心同 dy」。
