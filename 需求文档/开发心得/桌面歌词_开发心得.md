## 二、功能实现概要

- 实现功能点：
  - 桌面端专属透明置顶歌词条：双行（当前句高亮 + 下一句）、间奏「♪ 间奏 ♪」占位、
    无歌词「歌名 · 歌手」、未播放「未在播放」；字号三档（小/中/大）、任意拖拽、✕ 关闭、
    恢复默认位置，全部持久化（`desktopLyrics.enabled/fontSize/offset`）。
  - 仅桌面端出现设置分组（`DeviceType` 断点 + `Platform.isDesktop` 双门控），移动端 stub 不编译原生代码。
- 核心组件/服务：
  - `services/desktop_lyrics/lyric_window_api.dart`：`LyricWindowApi` 接口 + provider 注入
    （桌面真实现 / 移动 stub），业务零依赖 desktop_multi_window。
  - `lyric_bar_messenger.dart`：**纯 Dart** 跨窗口契约（状态/配置/回传事件编解码 + 容错回退），
    主窗口与子窗口共用，contract 可单测。
  - `lyric_window_desktop.dart`：真实现 + 几何纯函数（`lyricBarWindowSize`/`defaultLyricBarPosition`/
    `clampLyricBarPosition`）；窗口**只建一次复用**（open 时已存在 → configure+show）。
  - `desktop_lyrics_controller.dart`：`Notifier<bool>` 镜像开关偏好；歌词行状态经
    `select` 去重节流（行内进度不推送），消息 `==` 相等不下发；回传事件（✕/位置）只写偏好，
    窗口同步全部交给响应式重建——单数据流，无命令式分支。
  - `ui/desktop_lyrics/desktop_lyrics_bar.dart` + `lyric_bar_app.dart`：歌词条 UI 与子窗口
    Flutter 引擎入口（`runLyricBarWindow()`），拖拽走 `windowManager.startDragging()` 原生模态。
  - 三端 runner 注册：`setOnWindowCreatedCallback`（macOS Swift / Windows C++ / Linux C），
    仅对多窗口子进程应用无边框透明置顶样式，主窗口不受影响。
- 关键技术点：desktop_multi_window 的子 FlutterEngine 无法销毁 → 开关切换走
  hide/show/configure 而非创建/销毁；`LyricWindowConfig ==` 幂等去重避免重复下发。

## 三、遇到的问题与解决（坑）

### 坑 1：`WidgetsBinding.instance` 在纯 `test()` 未初始化 → 编排链被静默吞掉
- **现象**：控制器测试全部失败（窗口未打开/偏好未写入），但无异常栈——`unawaited(_syncWindow(...))`
  把错误吞进孤儿 Future，测试只表现为「什么都没发生」。
- **根因**：`_buildConfig` 用 `WidgetsBinding.instance.platformDispatcher.platformBrightness`
  判断暗色；纯 `test()`（非 `testWidgets`）没有初始化 WidgetsBinding，直接抛
  `Binding has not yet been initialized`。
- **解决**：改用 `dart:ui` 的 `PlatformDispatcher.instance.platformBrightness`——无需 binding、
  生产语义等价（WidgetsBinding.platformDispatcher 本就是它的转发）。
- **教训**：控制器/服务层应尽量依赖 `dart:ui` 级 API 而非 WidgetsBinding，可测性天然更好；
  `unawaited` 的后台链路要在测试里主动验证副作用，否则异常被吞。

### 坑 2：Riverpod 3 所有 Provider 默认 autoDispose → 测试里控制器「读完即焚」
- **现象**：`container.read(controllerProvider)` 后无论怎么 pump，窗口都不打开、事件订阅不生效。
- **根因**：测试里只有 `read`（临时订阅，读完释放）→ 控制器元素失去监听者即被销毁 →
  `_syncWindow` 的 `ref.mounted` 守卫直接 return、`events.listen` 被 `onDispose` 取消。
  生产中 `MyApp` 的 `ref.watch` 恰好充当常驻保活，掩盖了该语义。
- **解决**：测试用 `container.listen(controllerProvider, (_, _) {})` 挂持久 listener 保活
  （等价于生产 MyApp 的 watch）。`ref.mounted` 守卫本身是对的——它正确拦下了销毁后的同步。
- **教训**：Riverpod 3 的 autoDispose 默认值改变了「read 一下就算初始化」的旧直觉；
  凡是「全局单例型 Notifier」，要么有常驻 watch，要么在测试里显式保活。

### 坑 3：`ProviderContainer.pump()` 不级联刷新依赖重建
- **现象**：保活后仍偶发同步不到：偏好从 AsyncLoading→AsyncData 后，控制器重建没有随之发生。
- **根因**：`pump()` 只 `await scheduler.pendingFuture`——等的是**当前**这一批调度，
  不追级联（依赖变更 → 标脏 → 新一轮调度）。
- **解决**：测试 settle 改为循环冲刷（`for 8 次 { await pump(); await Future.delayed(Duration.zero); }`），
  覆盖微任务与调度级联。
- **教训**：Riverpod 测试的「等一下」要写成有界循环而不是固定次数；链路每多一跳 Async，
  就多一轮 pendingFuture。

### 坑 4：C/C++ runner 在 macOS 上的 21 条「编译错误」全是分析器假阳性
- **现象**：给 linux/windows runner 加插件注册回调后，clangd 报 21 条 STOP 级错误
  （`'gtk/gtk.h' file not found`、`flutter::` 未知类型等），且行号落在未改动的模板代码上。
- **根因**：在 macOS 上分析 Linux（GTK 头）/ Windows（Win32 头）runner，交叉头文件路径不存在，
  错误沿 include 链级联放大；与本次改动无关。
- **验证方法**：`git stash` 恢复未改动的原始模板 → 跑同样的诊断 → 报**一模一样**的错 →
  `git stash pop` 恢复改动。即「原始模板也报错 = 环境误报」的对照实验。
- **教训**：跨平台仓库里 LSP 对非宿主平台原生目录的诊断不可直接采信；
  analysis_options 已排除 platform 目录，DoD 以 `flutter analyze`（lib/ + test/）为准。
- **附带坑**：pi-lens 的 advisory `lyric_window_api.dart 引用 lyric_window_desktop.dart` 在文件
  创建后仍多次出现（缓存过期），以 LSP 全量扫描 + analyze 双绿为准忽略。

### 坑 5：macOS 上 `windowManager.show()` 会抢焦点
- **现象/风险**：`window_show` / `windowManager.show()` 内部走 `NSApp.activate`——用户点歌词条
  任意位置都会把主应用拉到前台，违背「点击不抢焦点」需求。
- **解决**：macOS 自建 `zeromusic/lyric_window/orderFront` 原生通道，MainFlutterWindow.swift 里
  `orderFront(nil)`（只显示不激活）；borderless `CustomWindow` 不覆写
  `canBecomeKeyWindow` → 天然不成为 key window。非 macOS 平台 `stealsFocusOnClick = true`
  并在设置页如实提示。

### 坑 6：细节备忘
- **AnimatedSwitcher 没有 `curve` 参数**——曲线要写在 transitionBuilder 的 Tween 里；
  用对称 Tween（`Offset(0,-0.6)→zero`）让出句复用入场动画反放，一行代码同时满足
  「新句下滑入、旧句上滑淡出」。
- **flutter_riverpod 3 的 `Override` 类型移到了 `misc.dart`**，`import 'package:flutter_riverpod/misc.dart'`
  才能在测试辅助函数签名里用 `List<Override>`。
- **间奏态单行设计**：`currentText == ''` 时第二行整体不渲染（而非显示下一句），
  避免间奏标记与下一句并排的割裂感。
- **`WindowController` 的 Dart 侧 API 很薄**：无 `close()`/`setFrame()`；`WindowMethodChannel.invoke`
  的 `mode:` 是命名参数——封装进 `LyricBarWindowCommands` 隔离，别让业务碰原始 API。

## 六、缺陷修复回补（2026-09，首次真机验证前）

> 首轮实现虽单测全绿，但 macOS 原生层从未编译过、且跨窗口初始化时序有硬伤，
> 真机首开即暴露。以下三个坑均为「单测绿 ≠ 功能可用」的实证。

### 坑 7：`FlutterViewController` 没有 `window` 成员 → macOS 整包编译失败
- **现象**：`flutter build macos` 直接失败：`value of type 'FlutterViewController' has no member 'window'`。
- **根因**：`setOnWindowCreatedCallback` 回调拿到的是 `FlutterViewController`（NSViewController
  子类），取宿主 NSWindow 必须经 `view.window`（此刻 `contentViewController` 已挂载，view
  必在窗口层级内）。想当然写了 `controller.window`，而 runner 代码不参与 `flutter analyze`，
  提交前也没跑过原生构建。
- **教训**：动了 runner / 原生插件的提交，DoD 必须加 `flutter build <platform>`，
  analyze + test 双绿不够。

### 坑 8：`hiddenAtLaunch` 创建的窗口「首次打开永远不出现」
- **现象**：首次开启开关（或重启自动恢复）歌词条不出现；只有关→再开（走复用分支
  configure+show）才出现。
- **根因**：窗口以 `hiddenAtLaunch: true` 创建（为避免错误位置闪现），但 show 只存在于
  「复用已有窗口」分支；首次创建路径上主窗口、子窗口都没人调 show。
- **解决**：增加 **ready 握手**——子引擎注册完 push handler 后回发 `ready` 事件；主窗口
  收到后才下发 show 并立即补推当前态。顺带修复另一个时序缺陷：冷启动窗口期的行推送
  会因子引擎尚未注册 handler 被通道丢弃（丢一行就要等下一次行变更，最长半分钟）。
- **教训**：跨窗口/跨进程初始化要显式握手（ready 信号）而不是双方各自猜时序；
  「创建时隐藏、就绪后显示」的模式里，show 的触发者必须唯一且由就绪方通知。

### 坑 9：关闭再重开后展示陈旧行
- **现象**：✕ 关闭后再开，歌词条停在关闭前的那一行（直到下一次行变更）。
- **根因**：隐藏期间推送被抑制（`_open == false` 时 pushState 直接丢弃），复用路径的
  `configure` 虽携带最新 `initialState`，但子窗口只更新了 `_config` 没应用到 `_state`。
- **解决**：① 子窗口 `didUpdateWidget` 应用 `config.initialState`；② 控制器在 `open()`
  完成后即推一次当前态（fake/测试可断言，真实路径由 ready 补推兑底）——双保险。
- **教训**：配置消息携带状态快照时，消费端要真正应用它；「暂停推送」的通道必须
  在恢复可见的那一刻做状态对齐，否则视觉层永远停在暂停点。
